openRag

openRag — Architecture

openRag is a TypeScript package that lets any chatbot answer questions from your own documents. You bring the documents and an LLM. openRag reads the docs, finds the right parts for each question, and gives back an answer along with its sources. It's also the first building block of a bigger chatbot framework for companies.

Where openRag fits

The long-term goal is one chatbot framework that any company can add to its website. It adjusts to each company's data, rules and permissions, so nobody has to build a new chatbot from scratch every time.

Not every question needs the same kind of lookup. An order status lives in a database, live stock comes from an API, and a refund policy lives in documents. So the framework has several tools and picks the right one for each question. openRag is the tool for documents, and we're building it first.

In one minute

Who brings what

You bring

  • Your documents: a folder, some files, or website links.
  • An LLM: an API key (Anthropic or OpenAI), or a free local model through Ollama.
  • Your chat screen, or no screen at all if you only use openRag as a tool.

openRag brings

  • Reading your docs and splitting them into small pieces.
  • A built-in store and embedder that run on your machine, so there's no server to set up. The exact ones are picked by the M0 experiments.
  • A search that finds the right pieces for each question.
  • An answer with its sources, written by your LLM.
  • Conversation handling: memory, follow-ups, asking back, and "that's not in the docs".
  • A step-by-step record of every answer.

One question, start to finish

  • Before any question: your docs are read, split into pieces, and saved along with their embeddings (numbers that capture meaning). This runs once, and again only for docs that change.
  • A user asks something. openRag first decides: answer straight away, search the docs, or ask the user what they mean.
  • If it searches: it looks for the best pieces two ways at once, by exact words and by meaning.
  • If nothing good turns up: it says the answer isn't in the docs instead of guessing.
  • Otherwise: it sends the question plus the best pieces to your LLM, which writes the answer with sources.

How to use it

Four ways to use openRag

Start with the simplest one. Each level works without the ones after it, and later versions make Level 1 smarter without you changing any code.

Level 1: point it at a folder

openRag finds your LLM key in .env on its own.

// .env → ANTHROPIC_API_KEY=…   (or OPENAI_API_KEY, or a running Ollama)
import { Bot } from "openrag";

const bot = new Bot({ sources: ["./docs"] });
const reply = await bot.ask("What is the refund policy?");

reply.answer      // "Refunds are accepted within 30 days…"
reply.citations   // [{ uri: "docs/refunds.md", heading: "Refunds › Window", score: 0.82 }]

Level 2: a real conversation, answers typed out live

Instead of waiting for the full answer, you get small events as they happen: what the bot decided, each word, each source. session tells openRag which user's conversation this is.

const bot = new Bot({
  sources: ["./docs", "https://docs.example.com"],
  llm: anthropic("claude-opus-5"),
  store: pgvector(process.env.DATABASE_URL),
  abstain: true,
});

for await (const ev of bot.chat({ session: "user-42", message: "and for international orders?" })) {
  if (ev.type === "action")   ui.status(ev.action);      // what the bot decided to do
  if (ev.type === "token")    ui.append(ev.text);        // the answer, word by word
  if (ev.type === "citation") ui.cite(ev.citation);      // a source
  if (ev.type === "done")     log(ev.trace);             // the full record
}

// In a Next.js app, one line turns this into a live stream for the browser
export const POST = (req: Request) => bot.chat.toResponse(req);

Level 3: replace any part

Every part has a default. Swap in your own, or an add-on package.

const bot = new Bot({
  sources: ["./docs"],
  chunker:   myChunker,                             // your own way of splitting docs
  embedder:  voyage("voyage-3"),
  retriever: hybrid({ lexical: 0.3, vector: 0.7 }),
  reranker:  cohereRerank(),
  sessions:  redisSessions(process.env.REDIS_URL),
});

As a tool: for agents and the framework

No chat and no LLM call. Just "find me the right pieces", plus a flag that says whether anything good was found.

const kb = new Bot({ sources: ["./acme-docs"], namespace: "acme" });

const result = await kb.retrieve("refund policy for international orders");
result.chunks     // best pieces, each with source, heading and score
result.grounded   // false → try another tool, or ask a human

const tool = kb.asTool();   // { name, description, inputSchema, run }: plug into any agent

Part 1 · Reading docs
Figure 4 · Reading your docs

Reading your docs: only what changed

Each document gets a fingerprint (a content hash). When you index again, openRag compares fingerprints. New or edited docs are processed, unchanged docs are skipped, and deleted docs are removed from the store. So after one small edit, re-indexing a big folder is quick.

flowchart TD
  S["Your docs
folder · links"] --> L["Loader
list + read files"]
  L --> H{"Fingerprint
changed?"}
  H -->|no| SKIP["Skip it"]
  H -->|yes| PA["Parser
clean text from md · mdx · html · txt"]
  PA --> CH["Chunker
split by headings · max 256 tokens"]
  CH --> EM["Embedder
pieces → numbers, in batches"]
  EM --> ST["Save to store
piece + numbers + word index"]
  L --> GONE["Docs that were deleted"]
  GONE --> DEL["Remove from store"]
  • Split by headings. Pieces break at the doc's own headings first. Each piece remembers where it came from (Refunds › International › Window), and that path shows up in the sources. How big each piece should be is decided by an experiment in M0.
  • File types in v1: Markdown, MDX, plain text and HTML. PDF comes later as an add-on, because reading PDFs well is heavy.
  • No repeat work. Each piece has its own fingerprint too, so an unchanged piece inside an edited doc isn't embedded again.

Any database can be plugged in as the store if it can do four things: save pieces, delete pieces, search by meaning and search by words, each inside a namespace.

Part 3 · Search
Figure 6 · Finding the right pieces

Finding the right pieces

Two searches run side by side. Keyword search finds exact words like product names and error codes. Meaning search finds text that says the same thing in other words. The two result lists are merged into one ranking. Then the packer picks the best pieces that fit in the space the LLM allows.

flowchart TD
  Q["The question
rewritten to make sense on its own"] --> LX["Keyword search
exact words · top 50"]
  Q --> VX["Meaning search
embeddings · top 50"]
  LX --> F["Merge both lists
RRF"]
  VX --> F
  F --> RR{"Reranker
turned on?"}
  RR -->|yes| R2["Re-sort carefully
keep the best few"]
  RR -->|no| TK["Keep the best few"]
  R2 --> PK["Packer
drop repeats · join neighbours · fit the size limit"]
  TK --> PK
  PK --> OUT["Best pieces + scores
+ found-it flag"]
This whole box is retrieve(). No LLM is used here, which is why the framework's router can call it quickly and cheaply.
  • The reranker is on by default (D-017). It's a second, slower model that re-reads the question together with each of the top 20 pieces. Measured: without it, merging the two lists at equal weight actually hurts reworded questions (87% → 67%). With it, the best result (90%, and the best top-1). Cost: about 0.45 s per question. Turn it off and the merge automatically shifts weight to meaning search.
  • Neighbours get joined. If pieces 4 and 5 of the same doc both make the list, they're joined into one passage instead of arriving as two fragments.
  • Scores are kept. They decide whether the bot says "not in the docs", they set the found-it flag, and they go into the trace.

Part 5 · Conversation
Figure 8 · The planner

The planner: one decision per message

Before doing anything, openRag asks the LLM one short question: what should happen with this message? The reply has three parts:

  • The action: answer, search, or ask back.
  • The full question: the message rewritten so it makes sense on its own. "and for v7?" becomes "how do I install version 7?"
  • Topic changed? Yes or no.

These three could each be a separate LLM call. Doing them in one call keeps the bot fast. Small talk like "thanks" or "hi" skips the call completely.

Figure 9 · Trace

Every answer can explain itself

Each reply comes with a trace: a step-by-step record of what happened. It shows what was decided, what was found, how long each step took, and how many tokens were used. Developers use it to debug "why did the bot say that?", and the eval uses it to score answers. Later, the framework adds tool calls and approvals to the same record, and it becomes the audit log.

{
  "turnId": "t_8f2a",
  "action": "RETRIEVE",
  "steps": [
    { "step": "planner",   "ms": 412, "out": { "standaloneQuery": "refund policy for international orders", "topicShift": false } },
    { "step": "lexical",   "ms": 3,   "hits": 50 },
    { "step": "vector",    "ms": 9,   "hits": 50 },
    { "step": "fusion",    "ms": 1,   "topScore": 0.71 },
    { "step": "pack",      "chunks": 4, "tokens": 1830 },
    { "step": "grounding", "passed": true, "threshold": 0.45 },
    { "step": "generate",  "ms": 1904, "tokensIn": 2410, "tokensOut": 188 }
  ],
  "citations": ["docs/refunds.md#international"]
}

Saved as plain JSON on the reply. Optionally, the same steps can also be sent to tools like Langfuse or Phoenix through OpenTelemetry.

Open decisions

All nine are now decided. A-1 and A-2 were settled by measurement, not opinion: see experiments/m0/RESULTS.md.

#QuestionOptionsSuggestion
A-1 · lockedWho turns text into numbers (the embedder)?An online API (needs a key) · a small model on your machine (no key, bigger install)Locked (D-016): bge-small-en on your machine (33 MB). A-2 · lockedWhere are the pieces saved (the store)?One SQLite file · a pure-JavaScript store · LanceDBLocked (D-016): one SQLite file (sqlite-vec + FTS5). A-4 · lockedWhen does it say "not in the docs"?Search score too low · ask the LLM to check · bothLocked (D-008): both. The score check comes first (free). Then the LLM can also report "not found" in the same call that writes the answer. The score cut-off gets tuned in M6.
A-5 · lockedWhat does the live stream look like in code?A loop over events · callbacks · web streamsLocked (D-009): a loop over events (for await), plus toResponse() for web servers. Scope

What "done" means for v1

v1 is done when

  • A working bot over a folder of docs takes 3 lines of code or fewer.
  • Conversations work: follow-ups, asking back, "not in the docs", topic changes.
  • Every reply has sources and a trace.
  • It works as a tool: retrieve() and asTool() are used from an agent in one example.
  • It's compared with LlamaIndex on the same docs, including MTRAG-UN, and the results show where we lose too.
  • It's published under a name we own, with a README a stranger can follow.

Not in v1

  • A hosted service, logins, billing
  • Per-user permissions inside one company's docs (keeping companies apart is in v1)
  • Images and scanned pages
  • GraphRAG
  • Runtimes other than Node (Bun, Deno, edge platforms)
  • The router, SQL/API tools, actions and setup: later phases
Glossary

Words used on this page

WordMeaning
RAGRetrieval-Augmented Generation. First find the right pieces of your docs, then let the LLM answer using them.
LLMThe AI model that writes the answer, e.g. Claude, GPT, or a local model.
Chunk / pieceA small part of a document, a few paragraphs long. Search works on pieces, not whole files.
EmbeddingA list of numbers that captures what a piece of text means. Texts with similar meaning get similar numbers.
EmbedderThe model that turns text into embeddings.
Meaning search (vector search)Finds pieces whose embeddings are closest to the question's embedding. Catches the same idea in different words.
Keyword search (BM25)Finds pieces that contain the question's exact words, giving rare words more weight.
RRFReciprocal Rank Fusion: a simple way to merge two ranked lists. Items near the top of both lists end up on top.
RerankerA second model that re-reads the top results and sorts them more carefully. Slower, but more accurate.
TokenThe unit an LLM reads text in, roughly ¾ of an English word. LLMs charge per token and can only read so many at once.
Fingerprint (content hash)A short code computed from a file's content. Same code means the file hasn't changed.
NamespaceA label that keeps one company's data apart from another's inside the same store.
SessionOne user's conversation, with its history.
PlannerThe step that decides what to do with each message: answer, search, or ask back.
AbstainThe bot says the answer isn't in the docs instead of guessing.
GroundedBacked by pieces actually found in the docs.
Citation / sourceA link from the answer to the exact doc and section it used.
StreamingSending the answer word by word while it's being written, instead of all at the end.
SSEServer-Sent Events: the standard way a web server streams text to a browser.
TraceThe step-by-step record of how one answer was made.
Add-on (adapter)A small extra package that plugs a different tool into one part, e.g. Postgres as the store.
Tool / asTool()A function an AI agent can call. asTool() packages openRag as one.
RouterThe framework part (Phase 3) that picks which tool a question needs.
OllamaA free app that runs LLMs on your own computer.
pgvectorA Postgres add-on for meaning search. The usual choice for production.
MTRAG-UNA public test set of multi-turn conversations full of hard cases: follow-ups, unclear questions, answers that aren't there. We use it to measure openRag.
LlamaIndexA popular existing RAG library. We compare openRag against it.
